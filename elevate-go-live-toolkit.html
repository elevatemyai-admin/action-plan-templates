Onboarding SOP — Building a New Client, Start to Finish
One linear runbook. Matt or Tracy can run this solo without cross-referencing five other docs.

1 Intake + Populate, in One Pass

Claude · ~5 min · all in the same chat

Paste the discovery call transcript into a Claude chat. In that same message, also state which pricing tier was discussed/agreed. Ask Claude to do everything at once:

  • Extract business type, current tools, biggest time-sink, what they're nervous about, what's off-limits, the smallest realistic first win, who approves changes
  • Directly output the populated CLIENT, TECH_STACK, and PLAN code blocks, ready to paste in
  • Directly output the populated SOW config block, ready to paste in
Fallback, rare case only: if a call genuinely wasn't recorded, type the same list by hand from memory before it fades.
How to know which tier to use: this is a business decision, not something Claude should guess from a transcript. Either it was explicitly agreed on the call, or it's still open between you and Matt — decide first, then include it in the same message. Never let Claude infer or default a pricing tier.
2 Create the Empty GitHub Repo

Still a manual step — fine-grained tokens can't create brand-new repos, only push to ones that already exist.

  • Go to github.com, logged in as elevatemyai-admin
  • New repository, name it [clientname]-action-plan
  • Public or private, no README, no license
  • Settings → Developer settings → your fine-grained token → Edit → add this new repo to its scope
3 Claude Pushes Everything Directly

No pencil-icon editing, no drag-and-drop upload — proven reliable across both Devon's and Alpine's builds.

  • Tell Claude the repo now exists and paste the token if it's a new session
  • Claude reads the master template + Step 1's blocks, populates index.html, sow.html, api/chat.js, and api/thoughts.js
  • Claude validates each file's JS syntax before pushing, then pushes all four directly into the new repo
  • In api/thoughts.js, confirm REDIS_KEY matches this client's CLIENT.slug — Claude should set this correctly on its own, just worth a glance
If Claude ever can't push (expired token, missing repo scope), fall back to the old pencil-icon method: click the file in the repo → pencil icon → paste the block → commit.
4 Deploy to Vercel
  • vercel.com → Add New → Project → Import the new repo
  • Framework preset: Other → Deploy
  • Settings → Environment Variables → add ANTHROPIC_API_KEY (same key already in use — if it ever comes back "invalid," generate a fresh one in console.anthropic.com rather than debugging the copy)
  • Storage tab (top-level, not inside the project) → find the existing Upstash Redis database → Connect Project → select this new project. This wires up KV_REST_API_URL/KV_REST_API_TOKEN automatically — needed for "Drop a thought" to work
  • Redeploy once all env vars are saved (Deployments tab → ⋯ on the latest one → Redeploy)
Test both live chat boxes before sending: "Talk it through" should get a real reply, and "Drop a thought" should actually save and reload on refresh. Visiting /api/thoughts directly in the browser shows the raw API response if something's off.
5 Send It
  • Grab the live .vercel.app URL
  • Send to the client — their action-plan page links to their SOW itself, so one link covers both
45-75 minutes
total time per client with Claude pushing directly — adjust once you've run this leaner flow a couple more times
SECTION ②
Value-Framing Rewrite Pattern
A pattern to apply, not a doc to write. Two real examples so Step 1 above has something concrete to copy.
Instead of thisWrite this
"Pull and segment your first 500 test contacts" You give us: 1 hour reviewing your export together. You get back: the 3-4 hours you'd otherwise spend manually cross-referencing it yourself.
"Send one test newsletter to the first 500" You give us: 15 minutes approving one draft. You get back: a finished newsletter — the part that normally eats half a day.
If you don't have a real number, say so honestly rather than guessing — "roughly 2-3 hours for most small businesses" is fine; a fabricated precise number is not.
New field pair: if a step has a genuine before/after hour estimate, also include timeNow and timeWithAI (in hours) alongside the usual youGive/youGetBack text. When both are set, the step shows a visual "Now vs. With AI assist" bar comparison instead of the plain chip. Leave both out for strategic or exploratory steps that don't have a clean before/after — forcing a number onto those is worse than showing nothing.
